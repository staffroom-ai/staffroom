Why this can win

The research is clear: nobody permissive has shipped a spatial "AI staff" product. What exists is either restricted (agents-office is PolyForm Noncommercial, AI-Employee is source-available, Dify/n8n/Flowise/Suna all restrict commercial resale) or a toy with under 20 stars. The big MIT projects (AnythingLLM, LibreChat, Langflow) are chat boxes or node graphs, not a team.

So the position is simple and defensible:

  • The only one you can build a business on. Apache-2.0 with a patent grant. Lead with this in the README.
  • The only one where each agent picks its model. Your copywriter on Claude, your data cleaner on a cheap model, your private-notes agent on a local Ollama. Nobody does this at the agent level.
  • The office is the demo. A 30-second GIF of agents walking to desks and lighting up connectors is what gets shared. Chat logs are not.
  • Local-first, files not databases. Your brain is a folder of markdown you already own. Delete the app and your notes are still there.

The honest caveat. agents-office has 118 stars after six months. The idea is appealing but demand is unproven. Popularity will come from execution and launch, not the concept alone. Budget for that.

Licence, done right

Apache-2.0 over MIT. Both are "absolutely free", but Apache adds an explicit patent grant, which is what corporate legal teams look for before they let staff adopt a tool. It costs you nothing.

Things to get right on day one, because they are painful to fix later:

  • DCO sign-off, not a CLA. A Contributor License Agreement scares off contributors. The Developer Certificate of Origin (git commit -s) is what the Linux kernel and most modern projects use.
  • Every dependency permissive. Verified today: three MIT, @anthropic-ai/sdk MIT, openai Apache-2.0, ollama MIT. The Claude Agent SDK is not open source (all rights reserved, subject to Anthropic's terms), so we do not use it at all. The agent loop is ours: a few hundred lines of TypeScript on top of the plain provider SDKs. Same for MCP: use the official @modelcontextprotocol/sdk (MIT) for the wire protocol, nothing else.
  • Never look at agents-office source. Its licence forbids derived commercial work. Clean-room this: same category, your own design. Delete the clone.
  • No telemetry by default. Opt-in, anonymous, documented. Silent phone-home is the fastest way to a hostile HN thread.
  • Trademark the name (or at least own the domain and npm scope) so the licence can stay permissive while the name stays yours. This is how most successful Apache projects handle forks.

What v1 is

One sentence: you type a task, the right agent walks to its desk, reads your notes, does the work, and files the result back into your notes for approval.

In scope

  • 3D isometric office: six departments as pods, agents at desks, idle / working / waiting-for-you states visible from across the room.
  • Roster in a YAML file: name, role, what they do, which model, which connectors. Rename freely.
  • Task bar: pick a department, type plain words, the lead agent picks the worker.
  • Per-agent chat, grounded in the brain. revise: reworks the last deliverable.
  • Brain: a folder of markdown. Indexed for search; rendered as a graph on G.
  • Approvals: any deliverable that would leave the machine waits for a click.
  • Routines: "every weekday at 8am" on the task bar.
  • Tools, two ways: any MCP server the user configures, or a custom tool they write as one file in office/tools/. Both look identical to an agent. Logos light up when used.
  • Demo mode: opens with a sample studio and canned runs, no keys needed.

Out of scope for v1

  • Multi-user, auth, cloud hosting. One person, one machine. Say so plainly.
  • A visual workflow builder. Langflow owns that; don't compete.
  • Custom office layouts. Six pods, fixed seats. Flexibility comes later, once the metaphor has proven itself.
  • Fine-tuning, RAG pipelines beyond the markdown brain.

Per-agent models

Yes, and it should be a headline feature rather than a setting. Each agent declares a model; the office declares a default; the runner resolves agent.model → office.default → first configured provider.

# office/agents.yaml
default_model: anthropic/claude-sonnet-5

agents:
  - id: copywriter
    department: marketing
    name: Priya
    role: Copywriter
    does: Turns briefs into landing page copy and email sequences.
    model: anthropic/claude-opus-5        # quality matters here
    tools: [notion, gmail]

  - id: bookkeeper
    department: finance
    name: Sam
    role: Bookkeeper
    does: Categorises transactions and drafts the monthly summary.
    model: ollama/llama4                  # never leaves the machine
    tools: []

  - id: researcher
    department: sales
    name: Lee
    role: Lead researcher
    does: Builds shortlists of prospects from a one-line description.
    model: openai/gpt-5-mini              # cheap, high volume
    tools: [web]

The adapter interface is deliberately tiny: complete(messages, tools, opts) → stream of text | tool_call | done. If it takes more than 150 lines to add a provider, the interface is wrong.

Tools: MCP and your own

Agents get tools from two places, and the agent never knows which. Both register into one ToolRegistry with the same shape: a name, a description, a JSON-schema input, and a handler.

1. MCP servers

Anything that speaks MCP, configured in office/config.yaml. The office runs its own MCP client (official @modelcontextprotocol/sdk, MIT), so it does not depend on Claude Code being installed. stdio and HTTP transports both supported.

# office/config.yaml
mcp:
  servers:
    notion:  { command: npx, args: [-y, "@notionhq/notion-mcp-server"], env: { NOTION_TOKEN: $NOTION_TOKEN } }
    gmail:   { url: "https://mcp.example.com/gmail", auth: oauth }
  deny: [stripe]
  departments:
    slack: [marketing, ops]      # only these pods see it

2. Custom tools

One TypeScript file per tool in office/tools/. Hot-reloaded. This is how a business owner (or the person helping them) wires in their own database, an internal API, or a spreadsheet, without publishing an MCP server.

// office/tools/lookup-order.ts
import { tool } from "staffroom/core";
import { z } from "zod";

export default tool({
  name: "lookup_order",
  description: "Find an order by number and return its status and items.",
  input: z.object({ orderNumber: z.string() }),
  scope: "read",                       // read | write — write tools go through approvals
  departments: ["sales", "ops"],       // who may use it
  async run({ orderNumber }) {
    const r = await fetch(`https://shop.internal/orders/${orderNumber}`);
    return r.json();
  },
});

Three rules keep this safe for non-developers:

  • scope: "write" always goes through approvals. The tool author declares it; the office enforces it. A tool that forgets is treated as write.
  • Tools run in the server process, never in the agent's context. The model sees the schema and the result, nothing else.
  • Tools are per-agent opt-in via agents.yaml → tools: [lookup_order, notion]. Nothing is ambient.

Built-ins ship as tools too (web_search, brain_search, brain_write), so the registry is the only path and there is no special-cased code to learn.

Architecture

A TypeScript monorepo. Node for the runner because that is where the MCP client libraries and every provider SDK live; a React front end because that is what contributors know and what React Three Fiber needs.

packages/ core/ agent runner, provider adapters, task queue, brain index, MCP client. No UI, no HTTP. server/ thin Node server: HTTP + WebSocket, serves web/, exposes core. ~1 file per route. web/ React + React Three Fiber. The office. Talks to server over WS only. cli/ `npx staffroom` → checks Node, writes office/, starts server, opens browser. templates/ sample offices: agency, ecommerce, clinic, consultant. Each is agents.yaml + brain/. apps/ docs/ docs site (Astro Starlight or similar). Deploy on GitHub Pages. office/ the user's data, gitignored: agents.yaml, config.yaml, brain/, runs.sqlite

Decisions that matter

  • core has zero UI or network knowledge. This is what lets someone embed it in their own product, and what keeps tests fast.
  • The brain is files. brain/**/*.md with front-matter. An index (SQLite FTS5, optionally embeddings) is a cache and can be deleted. Deliverables are written back as new notes with written_by, task, tools_used in the front-matter. The graph is built from wiki-links.
  • Runs are a log, not state. Every run appends events (started, tool_call, chunk, approval_needed, done) to SQLite. The office replays them; a refresh loses nothing.
  • 3D is a render layer, not the model. The office reads one OfficeState object over WS. A contributor could replace three.js with a 2D canvas and nothing else changes. This is also how you keep the bundle honest.
  • One tool registry, two sources. MCP servers and local office/tools/*.ts files both register the same shape. Built-ins (web search, brain read/write) go through it too.
  • The agent loop is ours. Prompt assembly, tool-call dispatch, retries, streaming, run events: all in core, on top of the plain provider SDKs. No proprietary agent framework underneath.

Stack, pinned

  • TypeScript strict, ESM only, Node 20+
  • pnpm workspaces, Turborepo for build caching
  • React 19, React Three Fiber, drei for helpers, Zustand for state
  • Vite for web, tsup for core/server/cli
  • Vitest for unit, Playwright for the office
  • Changesets for versioning and changelog

Safety rules

This is a product for people who are not going to read the source. The rules need to be few, absolute, and shown in the UI.

  1. Read freely, act only when asked. Agents may read any connector. They may send, post, pay, delete or change anything outside this machine only when the task explicitly names that action.
  2. Everything outbound waits for approval by default. The approval shows exactly what will be sent and where. Users can whitelist per agent, per connector, after they have seen it work.
  3. No shell, no filesystem, no sub-agents for office agents out of the box. If an owner needs one, they write it as a custom tool with scope: "write" and it goes through approvals like everything else. The boundary is the feature; the tool file is the deliberate, visible exception.
  4. Deny-list wins. config.yaml: mcp.deny: [stripe] keeps a server visible in the bar but out of every agent's hands.
  5. Every deliverable states its tools. The note in the brain records which connectors were called, so there is an audit trail without a "security" feature.

Getting popular

Stars come from three things in this order: the README, the launch, and responsiveness. The code is table stakes.

The README

  • A 20–30 second GIF above the fold: task typed, agent walks to desk, works, connector lights up, deliverable appears. Record it at 2x speed. This one asset does more than everything else combined.
  • First line after the title: Apache-2.0. Free for commercial use. Every agent can run on a different model.
  • Install block within the first screen. Then "first five minutes". Then a comparison table against the restricted alternatives, stated fairly.
  • No badges wall, no emoji headers. Ten badges say "template", two say "maintained".

The launch

  • Pick a Tuesday–Thursday. Post to Hacker News as "Show HN" at 8–9am US Eastern, X/Twitter with the GIF, r/LocalLLaMA (lead with the Ollama story), r/selfhosted, r/SideProject. Product Hunt a week later once issues from HN are fixed.
  • Write the launch post as a builder, not a marketer: what you wanted, why the existing ones did not work (licence), what is rough. HN rewards candour and punishes hype.
  • Be in the thread for six hours answering everything. This is where the first contributors come from.
  • Follow with a short "what I learned from 1,000 installs" post two weeks later. It compounds.

The first 60 days

  • Reply to every issue within 24 hours, even to say "thanks, looking". Silence kills momentum faster than bugs.
  • Seed 10–15 good first issue labels before launch: a provider adapter, a template, a docs page. Give away easy wins.
  • Release weekly with a human-written changelog. People watch repos that move.
  • Open Discussions, not Discord. Discord splits your attention and is invisible to search. Add Discord only if the community asks.
  • Make the first three external contributors visible: thank them in the release notes.
